# Backend transition

This experimental profile moves the accepted native RG/reverse-text producer and token-version carrier to vLLM 0.32 and its required numerical dependencies. It does not complete compatibility for every historical environment or model configuration. The preceding branch retains the previous backend profile. Dependency resolution and CPU imports alone are not evidence of GPU correctness; acceptance receipts distinguish those gates from actual training and reload runs.

Installation is not an unqualified clean `pip check`: three reviewed static metadata corrections match upstream `f8016025`. NIXL 0.10.1 and CUTLASS DSL 4.8.0 select their genuine CUDA 13 payloads instead of also installing unconditional CUDA 12 defaults. ModelExpress 0.3.0 uses that NIXL selection and protobuf 6.33.6 despite its published `<6` bound; its actual generated protobuf code imported and roundtripped, but the full optional service was not exercised. Original wheel metadata and checker discrepancies are preserved with the dependency review. These bounded exceptions do not justify arbitrary ABI overrides; the actual FA4 conflict instead led to explicit deferral. The deployed Git-backed native packages use genuine wheels from clean pinned checkouts, with source/hash evidence, to retain their version metadata when source archives omit Git history.

The launcher explicitly enables the native scale-out HTTP routes required by `/inference/v1/generate`. This registers token/render endpoints; it does not configure disaggregated prefill/decode or KV transfer. The first candidate lifecycle attempt reached a real 403 endpoint gate before training; that failed attempt is retained. The serving adapter delegates request handling, routing and generation limits to the native token endpoint. Its final response converts numeric token IDs to the pinned renderer's literal `token_id:<id>` labels without recomputing or rounding log probabilities. Sampled IDs are checked against the returned token IDs. Top candidates, prompt log probabilities, completion-index weight spans and response metadata are retained. Existing compact routed-expert serialization remains a response boundary, not a new routing feature.

`processed_logprobs`, the existing dense V1 runner selection, FP32 head/router flags, policy/value objectives and model/optimizer/reduction precision defaults remain explicit. The FP32 head patch accepts the target's new `skip_gather` argument. Obsolete prompt-budget, Harmony-stop and Qwen newline patches are removed where the pinned implementation already supplies the behavior; `patch-source-review.json` records exact source evidence. The V1 padded-input scrub and the existing early ring-attention compatibility import remain necessary in this profile.

## Weight labels and failures

Startup responses have the engine's literal `default` label, which is an unknown comparable policy version. A successful full-weight filesystem or NCCL adoption is followed by publication of its integer policy-step label. An administrative reload without a step resets the label to `default`; it never leaves an earlier numeric label attached to new weights. Invalid step values are rejected before adoption.

The training client pauses all engines, attempts each full-weight update once, and resumes only after every adoption and label publication succeeds. A lost response or failed publication leaves engines paused: a non-idempotent NCCL receive cannot safely be retried without another broadcaster. Pause/resume retain their existing bounded retries. The direct update endpoint requires its caller to pause first; it does not create an atomic transaction by itself.

Read-only `/weight_info` and `/is_paused` expose the official engine state for validation and operations. Leave `VLLM_SERVER_DEV_MODE` disabled: its separate native update protocol collides with this profile's admin routes, and startup rejects it explicitly rather than silently replacing either protocol.

Known sampled-token labels describe the weights used for those sampled positions. Keep-mode updates retain an in-flight request's context and KV cache, so a label is not proof that its entire context was recomputed under those weights. New groups keep the existing version-specific cache salt. LoRA responses suppress the engine-global base-weight labels because that label cannot establish adapter provenance. Frozen sampling remains unknown for comparable live-policy observations.

## Explicit compatibility boundaries

- FlashAttention 4 is rejected for both actor and value model configurations before device initialization. Its required TVM-FFI version conflicts with the exact vLLM dependency; no metadata override is used to disguise that conflict. FA2/FA3 selection and defaults remain unchanged.
- The prior NIXL/routed-expert validation bypass is removed. Native vLLM 0.32 rejects the unsupported P/D plus routed-output combination and requires its supported runner for routed output. This unit does not import an unrelated P/D workaround suite or claim that optional profile works.
- Existing `model.rope_scaling` dict/JSON configuration uses the officially supported callable HF override. For flat text RoPE, it preserves checkpoint base frequency and partial rotation unless explicitly supplied by the caller, then uses native normalization and validation. Nested/layer-specific schemes fail explicitly. An explicit `vllm_extra.hf_overrides` remains a caller override of this setting; no automatic merge is inferred.
- Sampling-mask replay, new model families, new objectives and backend throughput improvements are outside this unit. The accepted native producer profile and its historical legacy/MM backlog are unchanged.

## Focused checks

The serving tests use genuine target protocol classes and the real upstream final response generator. `config_probe.py` exercises the actual launcher/config loader, preserves flat Qwen/Llama RoPE parameters across dict/JSON aliases, checks invalid inputs, and verifies early FA4 rejection. Runtime harnesses and their source-guarded receipts record the bounded GPU pipeline, critic and weight-adoption checks separately. Source review and CPU tests must not be represented as completed GPU acceptance.

## Compiled attention compatibility

Torch 2.13 rejects the shared query/key sequence-boundary tensor inside the public FlashAttention autograd wrapper. In a checkpointed layer this produced eager fallback despite entering the compiled callable. The adapter therefore selectively uses upstream opaque FA2/FA3 forward/backward operations in `layers/flash_attn_ops.py`; kernel options, BF16 tensors and the existing deterministic flag remain unchanged. The independent ring/Ulysses implementations are unchanged and receive no new compiled-execution claim.

`attention_op_probe.py` compares the real public kernels with eager and fullgraph opaque calls, including full query/key/value gradients, shared boundaries, sliding windows and FA2 padded head dimensions. It first checks exact public repeatability and preserves tensors on failure. The existing compiled critic gate still requires actual captured graphs and its original numerical bounds; finite updates or profiler region markers alone do not establish acceptance. All four real-kernel cases passed with exact outputs, full gradients and strides against the public kernel, including exact public repeat controls and real fullgraph capture. The final identical-harness, two-rank/two-update critic comparison also passed: all 22 initial tensors and all 244 compared tensors were exact, with two captured graphs per rank. This covers the tested BF16 shared-attention path, checkpointed FSDP critic, FP32 optimization, dummy-rank masking, gradients, Adam states and updates; it is not a model-family or context-parallel compilation guarantee.

The earlier eager-fallback attempt remains recorded: zero captured graphs and 53 of 244 numerical comparisons outside their original bounds. The correction changed the attention integration, not the acceptance criteria. No tolerance, dtype, loss or value-function changes were used to obtain the final result. See the source-hashed `compile-source-review.json` and `independent-numerical-final002.json` receipts in the validation archive.

The full pinned Qwen3-4B fresh/resume lifecycle passed on both profiles: filesystem baseline and NCCL candidate each completed actor steps1–3, restored checkpoint3 and completed step4 with natural process exits. The candidate restored saved token/sample counters exactly (2886/6), then finished at3868/8; the sample counter is the implementation's counter, not a reconstructed rollout count. Candidate critic versions1–2 then3 were saved/restored correctly. The baseline uses filesystem and candidate NCCL deliberately; stochastic trajectories and differing unused tail critic work are not claimed to match across stacks.

A separate actual filesystem server adopted the trained checkpoints3 and4, whose saved weights have a verified tensor difference. A naturally generated4096-token response crossed from version3 for positions[0,16) to version4 for[16,4096). Raw responses passed through the pinned renderer, Episode and physical carrier with exact coordinates/log probabilities. Startup and an unlabelled reload remained unknown; a missing-checkpoint reload failed and left the engine paused at version4. This proves the tested dense sampled-weight attribution path, not recomputation of an in-flight request's cached history or a full environment scoring run.

The real NCCL lifecycle exposed a finite-run shutdown deadlock: the actor intentionally omits final broadcasts, while the old orchestrator waited for an additional batch before entering drain mode. The orchestrator now enters its existing train-only drain path after the successful final shipment completes metrics and its eval trigger. Already-triggered evaluations still finish, and shutdown waits for the NCCL broadcasts the trainer still promises before releasing their receiver. Objective, publication and value rules are unchanged. Correct termination may produce fewer unused tail rollouts and critic updates, so resume compares the actual saved critic version instead of assuming a fixed count. The resumed trainer also sends its fully restored checkpoint through the existing NCCL communicator before waiting for another training batch. The orchestrator receives that startup transfer without a filesystem marker path and only then publishes the restored version and opens rollout sources. Filesystem resume still loads its existing artifacts. Seven focused lifecycle regression cases and the corrected real fresh/resume rerun passed. The failed403 and shutdown-deadlock attempts remain in the evidence archive; neither is counted as a successful lifecycle.


## Accepted evidence and limits

The private [Resolution research record](https://github.com/resolutionorg/siddarth-research-cache/tree/main/projects/prime-values/records/2026-11-05-backend-sync) contains original criteria, full tiny numerical states, actual source/dependency manifests, failed attempts, real pipeline logs, raw response/carrier evidence and independent reviews. Runtime archive SHA256 is `021c4e27f623c21ead25800659528a48686ce41a431600801fff2b72adc0ca34`. No production value-function, loss, GAE, TETHER or optimizer/reduction precision changes were needed. The trainer startup hook and orchestrator lifecycle correction are transport/control-flow changes with their own regression and runtime evidence.

Acceptance is scoped to the recorded dense single-pool profile and tested kernels. It is not a guarantee for all model families, multi-node operation, LoRA, disaggregated serving, arbitrary rollback against stale broadcast markers, cross-stack checkpoint compatibility or improved training reward/throughput. Optional dependency exceptions remain explicit above.
